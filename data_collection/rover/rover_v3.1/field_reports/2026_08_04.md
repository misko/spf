# Rover engineering report — 2026-08-04

## Executive summary

Rover 4 entered the fleet. Bringing it up exposed **eleven** defects, of which
nine are fixed and pushed. Every one of them shares a single cause: Rover 4 is
the first rover built purely from what is written in this repository, and the
repository did not contain everything a rover needs. Rovers 1–3 work because
people configured them once, years ago in some cases, and the knowledge stayed
in their heads and in long-lived machine state.

The fleet ends the day healthy — all four rovers on `3486461`, clean checkouts,
all services active, all compass policies passing — and having produced two
multi-rover capture sessions that have not yet been merged or analysed.

Two findings would have silently corrupted data if left alone: **Rover 4 is in
the wrong timezone**, and **one of its receive channels was dead**. Neither
produced an error anywhere. The dead channel has since been traced to two
faulty antennas — one missing its pole, one fitted with a short pole — and the
same asymmetry, in milder form, is present on every receiver of rovers 1 and 3.

## Part 2 — Root cause analysis

Eleven symptoms, three causes.

### Cause A — the repository was not the source of truth (#2, #3, #5, #6)

Every one of these worked on rovers 1–3 through knowledge that existed only in
a person or in machine state predating the current scripts. Rover 4 was the
first rover built strictly from the written record, so it found every gap at
once.

`rover install` is the sharpest instance: the step existed, in the right stage,
idempotent by design — and Rover 4 still missed it, because it ran that stage
two hours before the line was added and **nothing re-runs a provisioning
stage**. The fix was not to add the step again but to make the boot path
converge it, alongside the systemd units and Python dependencies it already
reconciles.

### Cause B — unpinned dependencies (#1, #4)

Each rover's Python environment is whatever PyPI served on its provisioning
day. The fleet currently runs:

```text
rover 1/2/3   numcodecs 0.12.1   zarr 2.17.1   pymavlink 2.4.42
rover 4       numcodecs 0.15.1   zarr 2.18.4   pymavlink 2.4.49
```

Three zarr versions are writing production datasets. `numcodecs` is now
pinned; the rest is not, and the divergence remains.

Pinning `zarr` without pinning what zarr imports from is not a pin.

### Cause C — an upstream library defect (#8)

Documented and shimmed in `spf/mavlink/pymavlink_compat.py`, applied by both
the CLI and the production collector — the collector reaches `magcal` from
Taranis CH10 in the field, where the crash would kill a live capture.

### Two calls in this session were wrong

Recorded because the reasoning error is instructive, not the conclusion:

- **Rover 2's boot failures were attributed to CH7 rebooting the flight
  controller.** `Request reboot` appears **zero** times in 24 h across all four
  rovers. The repeated ArduPilot boot banner was taken as proof of a reboot
  without ruling out other explanations first.
- **A `pip install -e .` triggered by the day's pushes was blamed** for Rover 4's
  numcodecs. The `dist-info` timestamp is `2026-08-03 12:48:06` — original
  provisioning, hours before any of it.

Both were stated with more confidence than the evidence supported. Check
timestamps and counters before asserting causation.

### Antennas, not radios — O1 resolved

Rover 4's channel 0 measured 23.9 dB below its sibling on r1 with the AGC
railed on 99% of frames. Physical inspection found the cause: **both
channel-0 antennas were faulty — one missing its pole entirely, the other
fitted with a short pole.**

The measurement had localised this correctly before anyone opened the vehicle,
and it is worth recording why, because the same reasoning applies next time:

| Comparison | Reading | What it excludes |
|---|---|---|
| r1 ch1 vs r1 ch0 | +23.9 dB | Not the emitter — one channel of the same radio saw it fine |
| r1 ch1 vs r0 ch1 | +2.1 dB | **Not the radio** — both radios agree closely on their good channel |
| r1 ch0 vs r0 ch0 | −15.8 dB | Isolates the fault to one channel's signal path |

A failed SDR degrades both of its channels. r1's *other* channel was the
strongest on the vehicle. That single comparison ruled out the radio, and the
boot log agreed independently: `dual-RX present`, firmware verified, no libusb
or IIO errors. Everything electrical was healthy; there was simply nothing
connected to receive with.

`rover radio signal` was built during this session for exactly this loop, and
prints those three comparisons by design.

**This raises a fleet question.** Channel 0 also runs 6–11 dB below channel 1
on *every* receiver of rovers 1 and 3, with the AGC railed around 70% of
frames — a milder version of the same asymmetry, on rovers nobody has
inspected. Rover 4's antennas were visibly wrong once someone looked. Whether
rovers 1–3 carry mismatched or damaged antenna sets is now an open question
that a bench inspection would answer in minutes, and it affects the phase
measurements in every dataset the fleet has recorded.

## Part 6 — Proposed v7 merge and analysis plan

The pipeline in `tools/run_pipeline.sh` already implements merge → precompute →
figures → metrics. Aug 4 needs three changes to it, and one new step in front.

### Why a new step in front

Session A is roughly 46 GB of receiver IQ. Steps 2–3 are GPU-hours. Rover 4's
radio has a channel that is 37.7 dB down and phase-incoherent, and we do not
yet know whether its Session A capture is affected. **Discovering that after
the precompute is the expensive way to find out.** A per-capture triage that
reads a few hundred frames answers it in seconds.

### Step 0 — stage and quarantine

```bash
BASE=/mnt/qnap01/mouse9911/rovers_august_2026
# Session B is still only on the rovers.
for id in 1 2 3; do
  rsync -a --info=progress2 \
    pi@192.168.1.$((40+id)):/home/pi/temp/rover_2026_08_05_00_2*_tag_RO$id.zarr \
    "$BASE/aug4/"
done
# The SITL capture is tagged RO4 but is Rover 2's config on a 47 mm array.
mkdir -p "$BASE/aug4_quarantine"
mv "$BASE/aug4/rover_2026_08_04_14_22_13_nRX1_circle_spacing0p05075_tag_RO4.zarr"* \
   "$BASE/aug4_quarantine/"
```

Raw captures are immutable; `rsync` copies, and the quarantine move is within
the staging area, not the rover.

### Step 0.5 — per-capture triage (new)

For each complete capture, read a bounded sample of frames and report per
channel: mean \|IQ\|, gain distribution, the fraction of frames with gain
railed, and cross-channel coherence. Fail a capture that shows a channel more
than ~20 dB down or coherence below ~0.1.

This is the O1 gate. It costs seconds per capture and decides whether RO4
enters the merge at all.

### Step 1 — merge, with RO4 added and the quarantine respected

`run_pipeline.sh` currently pairs `RO2` against `RO1` and `RO3` only:

```bash
--rxs "$RAW"/*_tag_RO1.zarr* "$RAW"/*_tag_RO3.zarr*
```

Aug 4 needs `RO4` added. Run `--dry-run` first: it produces the GPS-overlap map
in about two seconds per pair without copying IQ, which both verifies that
Rover 4's timezone has **not** affected pairing (the merge keys on GPS time,
which is absolute) and confirms Session A/B groupings before committing to the
copy.

```bash
DATE=2026_08_04 BASE=/mnt/qnap01/mouse9911/rovers_august_2026 \
  RAW=$BASE/aug4 MERGED=$BASE/merged_aug4 STEPS=1 tools/run_pipeline.sh
```

Expected: 3 RX × 1 TX in Session A (4 with RO4 if it passes triage), 2 × 1 in
Session B.

### Step 2–4 — precompute, figures, metrics

Unchanged from the Aug 1/2 runs, with the version-scoped cache:

```bash
DATE=2026_08_04 BASE=… RAW=$BASE/aug4 MERGED=$BASE/merged_aug4 \
  CACHE=/mnt/qnap01/mouse9911/precomputed/precompute_cache_3p7 \
  STEPS=2,3,4 tools/run_pipeline.sh
```

### Step 5 — complete this report

`df_metrics.py --markdown` prints the per-dataset table. Sections to add:

- **Merged direction-finding datasets** — the metrics table, matching Aug 2's.
- **First four-rover session** — whether RO4 contributed usable bearings, and
  how 47 mm spacing compares against 35 mm and 43 mm on the same emitter pass.
  This is the first opportunity to compare three spacings simultaneously.
- **O1 verdict** — whether the dead channel is confined to the SITL capture.

### What this plan deliberately does not do

- It does not rename or repair the quarantined SITL capture. It records what
  actually ran.
- It does not fix Rover 4's timezone before merging. The merge keys on GPS
  time, so a timezone fix would change filenames without changing pairing —
  better done as its own change, with the old names still traceable.
- It does not touch the thirteen `.zarr.tmp` stores. Renaming an interrupted
  temp store is forbidden by the runbook.
